# CBS Food Signup System (Google Forms + Sheets v1)

This design gives you a **simple no-login signup flow** now, while preserving a **clean data model** you can reuse later in a custom web app.

---

## 1) Data Model (Reusable for Future App)

Use stable IDs now (in Sheets) so migration to Supabase/Firebase/SQL is straightforward later.

### `events`
| Field | Type | Required | Notes |
|---|---|---:|---|
| id | string | yes | Stable unique ID (e.g., `evt_2026_09_10`) |
| date | date | yes | ISO-like display (`2026-09-10`) |
| title | string | no | e.g., "Weekly CBS Night" |
| description | string | no | Optional notes for participants |

### `slots`
| Field | Type | Required | Notes |
|---|---|---:|---|
| id | string | yes | Stable unique ID (e.g., `slt_evt_2026_09_10_main_1`) |
| event_id | string | yes | FK -> `events.id` |
| category | string | yes | Main, Side, Dessert, Drinks |
| item_name | string | no | e.g., Pasta, Salad |
| max_signups | integer | yes | Default 1 |
| current_signup_count | integer (derived) | yes | Calculated from signups |
| is_full | boolean/text (derived) | yes | `TRUE/FALSE` or `FULL/OPEN` |

### `signups`
| Field | Type | Required | Notes |
|---|---|---:|---|
| id | string | yes | Unique ID for signup (generated by Apps Script or formula) |
| event_id | string | yes | FK -> `events.id` |
| slot_id | string | yes | FK -> `slots.id` |
| name | string | yes | Participant name |
| email | string | yes | Participant email |
| notes | string | no | Optional dietary/coordination notes |
| created_at | datetime | yes | Submission timestamp |
| updated_at | datetime | no | If edited later |

## 2) Google Sheets v1 Structure

Create one Google Spreadsheet with these tabs:

## Tab A: `Events`
Admin-managed source of event choices.

**Columns (left to right):**
1. `id`
2. `date`
3. `title`
4. `description`
5. `display_label` (derived for form/admin readability)

Example `display_label` formula in E2:
```gs
=TEXT(B2,"yyyy-mm-dd") & " — " & IF(C2="","CBS Night",C2)
```

## Tab B: `Slots`
Admin predefines all slot rows for each event.

**Columns:**
1. `id`
2. `event_id`
3. `category`
4. `item_name`
5. `max_signups`
6. `slot_label` (derived)
7. `current_signup_count` (derived)
8. `open_spots` (derived)
9. `status` (derived, OPEN/FULL)

Formulas (starting row 2):

- `slot_label` (F2):
```gs
=IF(D2="", C2, C2 & " — " & D2)
```

- `current_signup_count` (G2):
```gs
=COUNTIF(Signups!$D:$D, A2)
```
(Assumes `Signups!D:D` is `slot_id`.)

- `open_spots` (H2):
```gs
=MAX(0, E2-G2)
```

- `status` (I2):
```gs
=IF(H2<=0, "FULL", "OPEN")
```

## Tab C: `Signups`
This is the **form response destination** (do not let users edit directly).

Recommended columns:
1. `form_timestamp`
2. `name`
3. `email`
4. `slot_id`
5. `notes`
6. `signup_id` (derived or script-generated)
7. `event_id` (lookup from slot)
8. `created_at` (copy timestamp)
9. `updated_at` (blank unless edit workflow used)

Suggested formulas:

- `signup_id` (F2):
```gs
=IF(A2="","","sgn_" & TEXT(A2,"yyyymmdd_hhmmss") & "_" & ROW())
```

- `event_id` (G2):
```gs
=IF(D2="","",XLOOKUP(D2, Slots!$A:$A, Slots!$B:$B, ""))
```

- `created_at` (H2):
```gs
=IF(A2="","",A2)
```

> Note: You can keep `form_timestamp` as Google Form’s built-in timestamp and map it to `created_at` for future migration consistency.

## 3) Google Form Configuration (Primary UI)

Create one form called **“CBS Food Signup”**.

### Required fields
1. **Name** (Short answer, required)
2. **Email** (Short answer, required; set response validation for email format)
3. **Event Date** (Dropdown, required)
4. **Food Slot** (Dropdown, required)
5. **Notes** (Paragraph, optional)

### Important form settings
- Enable **“Collect email addresses”** (optional if you already ask for Email; useful for verification).
- Enable **“Edit after submit”** so participants can revise.
- Show confirmation message with friendly next steps.
- Keep form short and mobile-friendly (single page if possible).

### Event + Slot selection strategy in Forms
Google Forms does not natively do robust relational filtering in a single dropdown without scripting. Use one of these:

1. **Simple v1 (fastest):**
   - `Event Date` dropdown from `Events.display_label`
   - `Food Slot` dropdown from a combined list like:
     - `2026-09-10 | Main — Pasta | slot_id`
   - Admin periodically refreshes choices (manual or Apps Script).

2. **Better v1.1 (recommended):**
   - Use **multiple-choice “Go to section based on answer”** for Event Date.
   - Each event section has its own Food Slot question with only that event’s slots.
   - Reduces wrong pairings significantly.

3. **Best v1.2 (scripted):**
   - Apps Script updates slot choices automatically from `Slots` where `status = OPEN`.

For clean data, include the **`slot_id` in the actual choice value** (human-readable text plus ID), then parse/extract into `slot_id` column.

## 4) Relationship Integrity in Sheets

To maintain reusable relational integrity:

- Treat `Events.id` and `Slots.id` as immutable primary keys.
- `Slots.event_id` must always reference existing `Events.id`.
- `Signups.slot_id` must always reference existing `Slots.id`.
- Derive `Signups.event_id` from `slot_id` lookup (not user-entered).
- Protect ID/formula columns from edits (Data > Protect sheets/ranges).

Validation suggestions:
- In `Slots.event_id`, use data validation referencing `Events.id`.
- In admin views, flag orphan rows with conditional formatting:
  - slot without event
  - signup with unknown slot

## 5) Admin Workflow

1. Add upcoming event rows in `Events`.
2. Add slot rows in `Slots` per event (set categories/items/max_signups).
3. Refresh Form choices (manual or scripted).
4. Share form URL with group.
5. Monitor `Slots.status` and `Signups`.
6. Export CSV from `Signups` when needed.

No participant ever touches sheets directly.

## 6) Optional Enhancements in Sheets/Form

## A) Helper view: Open vs Filled
Add `Helper_OpenSlots` tab using QUERY/FILTER:
```gs
=FILTER(Slots!A:I, Slots!I:I="OPEN")
```

## B) Conditional formatting
On `Slots`:
- If `status="FULL"` -> red fill.
- If `open_spots=1` -> yellow.
- If `open_spots>1` -> green.

## C) Public read-only status view
Create `Public_View` tab with only non-sensitive columns:
- event date/title
- category/item
- open/full
Then share that tab (or a published link) read-only.

## 7) Extensibility Path (Future Custom Web Frontend)

This sheet model maps directly to DB tables:

- `Events` -> `events`
- `Slots` -> `slots` (FK `event_id`)
- `Signups` -> `signups` (FK `slot_id`, `event_id`)

### Recommended backend mapping (Supabase/Firebase/SQL)

- Keep IDs as strings/UUIDs.
- Add unique constraints and indexes:
  - `slots(event_id)`
  - `signups(slot_id)`
  - optional unique rule to prevent duplicate signup by same email per slot/event.

### Real-time availability
- Compute `current_signup_count` server-side (or materialized view).
- Display `open_spots = max_signups - count` in UI.

### Overbooking prevention (critical)
In web backend, enforce atomically:
- Transaction:
  1. Lock/read slot
  2. Check count < max_signups
  3. Insert signup
  4. Commit

### Secure edit/cancel links
- Generate token per signup (`edit_token_hash`, `expires_at`).
- Email participant a private link (`/signup/edit/{token}`).
- Permit only token-based edit/cancel without account.

### Admin dashboard evolution
- CRUD for events/slots
- Live slot fill meters
- Filters by date/category
- CSV export

4. Add slots per event with max_signups values.
